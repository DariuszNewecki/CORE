### 3.1 Operational error observation (disclosed — not concealed)
The soak was **not error-free**. Journal analysis over the window found **288 Python tracebacks**
(= 288 ERROR-level lines), and **all 288 originate from a single source**:
`workers.scheduled_worker` (`src/shared/workers/scheduled_worker.py:84`, `run_loop`). Each
references `git_service` and a missing file `src/cli/resources/workers/_scratch_verify_769.py`
(432 total mentions). This is **one recurring defect firing ~every 15 min**, not 288 distinct
failures.

- **No restart resulted:** `run_loop` caught and continued each cycle; `NRestarts=0` held and
  the fleet kept producing entries throughout.
- **Scope:** isolated to one scheduled worker; the other ~34 workers show no such pattern.
- **Likely nature:** a stale reference to a scratch/verify artifact (`_scratch_verify_769.py`,
  apparently a leftover from #769-era work) that no longer exists on disk — persistent but
  non-corrupting. **Not independently confirmed as benign** in this report.

**Bearing on G4:** the autonomous *loop* maintained continuity (no stall, no restart), but "loop
reliability" was not clean — one worker was in a continuous error state for the full 72 h. The
governor should weigh this before signing `met`, and may wish to open a follow-up to clear the
stale reference. It does not, by itself, indicate a systemic loop failure.

## 5. Recommended verdict (for governor signature)

**The operational soak remained intact for the full 72-hour window and provides sufficient
evidence for G4.** The production baseline `f7430b25` ran uninterrupted with a
continuously-active worker fleet (68,495 blackboard entries, ~35 workers) and zero restarts.

**Reliability qualification (see §3.1):** the run was not error-free. One scheduled worker
(`workers.scheduled_worker`) threw a recurring traceback ~every 15 min for the entire window
(288 total, all from that single source, tied to a missing scratch file `_scratch_verify_769.py`).
It never caused a restart or a loop stall, but it means "loop reliability" was demonstrated at the
*continuity* level, not the *clean-run* level. The governor should decide whether this is
acceptable for `met` or warrants a `mostly_met` with a named residual + follow-up.

**One documented procedural exception occurred:** the docs-only anchor commit `f7430b25` was
created 49 minutes after service launch. The commit changed no executable source, `.intent/`,
configuration, database state, or running process, and therefore did not affect the behavior
under soak. Governor acceptance of this exception should be recorded explicitly in the G4
attestation. A second disclosed artifact — an untracked isolated-demo planning document in the
tree — likewise touches no protected surface.

**Scope boundary:** G4 attests autonomous-loop operational continuity only. It does **not**
validate the isolated consequence-chain demo, overall production readiness, or the demo
specification's Phase 0 implementation sequencing (see the companion deviation record for that
last point).

**Governor action required:** record the G4 verdict in
